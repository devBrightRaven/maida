Method: ripgrep over `src/`, `src-tauri/src/`, `e2e/`, `scripts/` for `lastPlayed`, `LastActivity`, `"Never"`, `activity_weight`, and for importers of every module that reads the field (`normalize`, `sort`, `stats`, `engine`, `GamePresence`, `data`). `e2e/` and `scripts/` have no hits.

## BUG-005 `activity_weight`

### Call sites

| Site | Reached in 2.0? |
|---|---|
| `src-tauri/src/commands/steam.rs:77-78` (dedup loop in `perform_background_snapshot`) | Yes, but only when the existing `games.json` holds two records with the same `steamAppId` |
| `perform_background_snapshot` <- `src/services/bridge.js:37` <- `src/hooks/useMaidaSession.js:65` | Yes, every session load |

Duplicates cannot come from a fresh scan: `scan_steam_library` dedups (`src-tauri/src/steam/mod.rs:160, 199-202`), onboarding overwrites `games.json` wholesale (`commands/steam.rs:19-35`), and the snapshot writes the deduped set back. So the branch heals a legacy file once. When it does run on Steam-written records, the played term was always 0 and the tiebreak used score only.

### Verdict: fix (applied)

Low impact, but the fix is small and routes the function through the LastPlayed contract.

- `src-tauri/src/commands/steam.rs:206` `activity_weight` now calls `has_played` (`:220`): if `steamLastPlayedStatus` is present, only `"recorded"` with an epoch in `0 < n <= MAX_EPOCH_SECONDS` counts; `zero` / `missing` / `invalid` / inconsistent pairs add 0. Without a status, the legacy `lastPlayed != "Never"` rule is kept so old files heal as before.
- `src-tauri/src/steam/mod.rs:28` `MAX_EPOCH_SECONDS` made `pub(crate)` so the bound is shared, not copied.
- Tests: `src-tauri/src/commands/steam.rs:235` `mod tests` (3 tests). `steam_recorded_play_outweighs_unplayed_duplicate` failed before the fix (`assertion failed: activity_weight(&played) > activity_weight(&unplayed)`) and passes after.

### Live half: `src/core/engine.js`

| Site | Path to UI |
|---|---|
| `engine.js:173-180` `daysSinceLastPlayed` | called from `:195` and `:226` |
| `engine.js:195` `long-absence-return` proxy | `getPrescription` -> `computeContextualMatches` -> `matchEmotionalProxy` |
| `engine.js:226-239` `return-after-absence` triggers | `getPrescription` -> `computeContextualMatches` |
| `engine.js:277-292` `isRepeat` / momentum | `getPrescription` |
| `getPrescription` callers | `src/hooks/useMaidaSession.js:80, 98, 146, 364` -> `session.prescription` -> `src/App.jsx:859` -> `src/views/RinView.jsx:401` -> `src/ui/features/Uncertainty/GameDisplay.jsx:29` (Rin prescription line) |

Test callers: `src/__tests__/core/engine.test.js` (22 lines feed `lastPlayed: 'Today' / 'Never' / dates`, ~430-552).

The real defect is not "missing / Never / invalid collapse into null". On 2.0 Steam records `game.lastPlayed` is always `undefined`, so for every Rin game:

- `new-device-start` ("Even without any record of playing this before...", criterion `no-last-played`, `src/data/prescriptions.json:1241-1256`) is always in the contextual pool, including games Steam says were played.
- The five gap-based `return-after-absence` entries (`prescriptions.json:1157-1240`) and the `long-absence-return` proxy never fire.
- `isRepeat` is always false, so the catalog/default filter always asks for `unlock`; `stabilize` lines are only reached through the unfiltered fallback.
- `post-anchor-gap` also never fires (and `context.previouslyAnchored` is never passed: every caller uses two arguments).

Verdict: **needs user decision**. A patch would route `engine.js` through `lastPlayedState()` (`src/core/lastPlayed.js:57`), which changes which prescriptions Rin shows. Open questions:

1. Does Steam `zero` (proven never played) satisfy `no-last-played`? Does `unknown` (missing / invalid / legacy)? The contract forbids treating unknown as "never played", but the `new-device-start` text speaks about the absence of a record, which arguably fits unknown too.
2. Should the 30% contextual injection start surfacing the gap-based return lines at all in 2.0 Rin, given they have been silent since the Steam switch?
3. `engine.test.js` ~430-552 would need rewriting to Steam-shaped fixtures.

Philosophy impact: unclear. Prescription text is permission, not recommendation, so red line 7.1 is not touched; the question is whether reviving these lines fits the 2.0 Rin posture.
